# ADR-002: 웹 업로드와 명시적 번역 실행

## 상태

채택. 2026-11-17 사용자가 정한 [웹 업로드 명세](../specs/web-upload.md)를 구현합니다. [ADR-001](ADR-001-react-and-intranet-boundaries.md)의 FastAPI·React·로컬 배포 경계를 유지하고, 기존 입력 감시·신규 자동 번역 흐름을 대체합니다.

## 맥락

사용자는 실제 운영에서 웹으로 문서를 올리고 번역 버튼을 직접 눌러야 합니다. 업로드 파일명은 자유여야 하고, 문서별 번호 충돌·미처리 판의 누적을 막아야 합니다. 기존 번역 엔진·파일 저장 구조를 재사용하며 패키지 설치나 작업 큐 도입은 하지 않습니다.

## 대안

1. 업로드를 inbox에 저장하고 감시 서비스가 처리: 파일명 변환과 감시 지연이 추가되고 기존 rev001 자동 번역 정책과 충돌합니다.
2. 웹 전용 등록 구현: CLI와 원본 보관·비교·잠금 규칙이 갈라집니다.
3. 웹과 CLI가 Pipeline 등록 경로를 공유: 기존 파일 잠금·원본 저장·비교를 재사용하면서 입력별 정책을 구분할 수 있습니다.

## 결정과 이유

- 3안을 채택하고 감시 명령·서비스를 제거합니다. `process`는 관리자 일괄 등록용으로 유지합니다.
- 웹은 `logs/.uploads/`에 스트리밍 수신하고, 검증·차이 준비를 마친 뒤 원본과 검토 폴더를 공개합니다. 설치된 Starlette/python-multipart 파서를 확장해 중도 크기 제한과 임시 파일 위치를 제어합니다. 별도 HTTP 서버·파서 구현은 추가하지 않습니다.
- 웹의 문서 상태 검사와 rev 부여는 기존 `flock` 안에서 수행합니다. 선택 화면의 요약은 안내이며 서버가 등록 시 재검사합니다.
- rev001을 포함한 새 등록은 모두 pending이며 승인 버튼 또는 CLI approve를 실행해야 번역합니다. 과거 auto_approved 상태는 읽기 호환을 유지합니다.
- 웹은 기준본 없는 개정과 처리 중 판이 있는 문서의 업로드를 거부합니다. 관리자 process의 기존 일괄 등록·기준본 없는 개정은 유지하므로 승인 시 기준본 재검사도 유지합니다.

## 결과와 제약

운영 서비스는 웹 하나이며 기존 감시 서비스는 운영자가 중지·제거해야 합니다. 등록 실패는 정리하지만 SIGKILL·정전에서 원본과 검토 폴더의 일괄 원자성은 보장하지 않습니다. 기존 직렬 잠금 때문에 긴 번역 중 등록이 기다릴 수 있습니다. 업로드 파서는 Starlette 내부 multipart 상태를 사용하므로 의존성 갱신 시 스트리밍·실패 정리 테스트를 실행해야 합니다.

`python-multipart`는 기존 설치 버전을 직접 의존성으로 선언했습니다. 잠금 파일 갱신은 사용자 담당이며 이번 작업에서 패키지 설치·실제 번역 API 호출은 하지 않습니다.
